01 LLM Ecosystem & Model Landscape

The big picture before touching any code: who builds models, closed vs. open, API vs. local, and how the pieces fit into a real application stack.

LECTURE
Topic 1 lecture PDF — teach me the LLM ecosystem & model landscape.

Core idea: The GenAI ecosystem = model providers + cloud platforms + open-source communities + developer tools. LLMs are becoming a core layer of modern software, not a standalone product.

CategoryWhat it means2026 examples
Closed modelsAPI-only access, weights hiddenGPT‑5.5/5.6, Claude Sonnet/Opus 5, Gemini 3.1
Open modelsWeights downloadable, self-hostedLlama 4, Mistral, DeepSeek V4, GLM‑5.2

The LLM stack: UI → Backend → LLM/Model API → Retrieval/DB → External Tools. The LLM is one replaceable layer, not the whole app.

UPDATELecture's model list was 2024-era. Real 2026 lineup and the OpenAI‑style tiers were swapped in — model names age fast, the categories don't.
LECTURE
Handwritten notes — "What are Models" in LangChain.

The Model component in LangChain abstracts the complexity of working directly with different LLMs, chat models, and embedding models — one uniform interface for all of them. This is what makes it possible to build apps around AI-generated text, similarity search, and RAG without rewriting code for every provider.

Models
├── Language Models
│   ├── LLMs
│   └── Chat Models
└── Embedding Models

The core distinction between the two branches, in one line each:

BranchInput → OutputExample
Language Modelstext → text"Capital of India?" → "Delhi"
Embedding Modelstext → vector"Capital of India?" → [0.02, -0.41, ...]

One generates language, the other generates a numeric fingerprint of meaning used for search/retrieval — this is the split your whole notes site is organized around (Chat Models = category 02, Embeddings = category 03).

LECTURE
Handwritten notes — Open Source Models, deeper dive.

Open-source language models are freely available models that can be downloaded, modified, fine-tuned, and deployed without restriction from a central provider — unlike closed models (GPT, Claude, Gemini), which lock you into the provider's infrastructure.

FeatureOpen-SourceClosed-Source
CostFree to use, no API costPaid, per-token usage
ControlModify, fine-tune, deploy anywhereLocked to provider's infra
Data privacyRuns locally, nothing leaves your serversQueries sent to provider's servers
CustomizationFull fine-tuning accessLittle to none, in most cases
DeploymentOn-premise or your own cloudMust use vendor's API

Two ways to actually use an open-source model: through a Hugging Face Inference API (hosted, no local setup) or by running it locally (full control, needs your own compute) — this exact fork is what the hands-on Chat Models section below walks through in code.

DISADVANTAGESHigh hardware requirements for large models · setup complexity (PyTorch, CUDA, transformers all needed) · most open models lack RLHF, so weaker instruction-following · limited multimodal support (no native image/audio/video like GPT-4V).
2026 UPDATEThe notes' "famous open source models" list (LLaMA-2, Mixtral-8x7B, Falcon, BLOOM, GPT-J, StableLM) is 2024-era. See Category 01's provider table above for the current 2026 lineup — Llama 4, Mistral, DeepSeek V4, GLM-5.2, Gemma 4 — same categories, newer generation.
DECISION
How does a developer actually choose which LLM to use?

Weigh: capability, latency, cost, context window, privacy requirements, deployment options. It's a systems design decision, not just "which model is smartest."

Rule of thumb: default to API models for speed of shipping. Switch to self-hosted/open only when privacy (data can't leave your servers) or extreme scale forces it.

02 Chat Models — Setup, Providers & Debugging

Environment setup, then hands-on with Anthropic, OpenRouter, and Hugging Face (both hosted and fully local) — plus every error hit along the way.

LECTURE
Handwritten notes — LLMs vs Chat Models, what's actually different?

LLMs — general-purpose models built for raw text generation. Take a plain string in, return a plain string out. Traditionally the older style, not used much anymore on their own.

Chat Models — language models specialized for conversational tasks. Take a sequence of messages as input (system / user / assistant roles) and return a structured chat message as output. The newer default, and what nearly everything in this notes site actually uses (ChatAnthropic, ChatHuggingFace, ChatOpenRouter).

FeatureLLMs (Base)Chat Models (Instruction-Tuned)
PurposeFree-form text generationOptimized for multi-turn conversation
Training dataGeneral text corpora (books, articles)Fine-tuned on chat/dialogue datasets
Memory & contextNo built-in memorySupports structured conversation history
Role awarenessNo concept of "user" vs "assistant"Understands system / user / assistant roles
Use casesText gen, summarization, translationChatbots, virtual assistants, coding agents
MY NOTEIn practice today, chat models are used far more than raw LLMs — conversational chatbots, coding agents, and similar tools all run on chat models. Base-LLM support inside LangChain itself keeps shrinking over time.
PARAMETER
What does temperature actually control?

temperature controls the randomness of a model's output — how creative vs. deterministic responses are. Lower = more predictable and repeatable, higher = more varied and surprising.

Use caseRecommended temperature
Factual answers (math, code, facts)0.0 – 0.3
Balanced response (general QA, explanations)0.5 – 0.7
Creative writing, storytelling, jokes0.9 – 1.2
Maximum randomness (wild brainstorming)1.5+

Ties directly back to the TinyLlama bug fixed below — temperature=0.5 only has an effect when do_sample=True is also set; otherwise the model defaults to greedy (fully deterministic) decoding and silently ignores it.

DECISION
pip install -r requirements.txt or uv?

uv is faster (Rust-based, 10–100x quicker dependency resolution) and drop-in compatible with existing requirements.txt files. pip is already built-in, matches what most tutorials show.

Verdict while learning: stick with plain pip — one less variable while following a tutorial. Switch to uv once comfortable and iterating on your own projects often.

CODE
Anthropic model call — is this 2026 standard?
DATEDOriginal used claude-3-5-sonnet-20241022 — an Oct 2024 snapshot. Still runs, but not what you'd use today.
from langchain_anthropic import ChatAnthropic
from dotenv import load_dotenv

load_dotenv()

model = ChatAnthropic(model='claude-sonnet-5')
result = model.invoke("write a poem about Love")

print(result.content)

Optional pattern for the future — pull the model name from env instead of hardcoding, so a provider's new release only means editing .env:

model = ChatAnthropic(model=os.getenv("ANTHROPIC_MODEL", "claude-sonnet-5"))

os.getenv("NAME", default) → looks for env var NAME; if missing, silently falls back to default. Not a special LangChain keyword — just Python.

ENV FILE
.env values — with quotes or without? Spaces around =?
# Correct:
OPENAI_API_KEY=sk-abc123xyz

# Avoid:
OPENAI_API_KEY = "sk-abc123xyz"   ← spaces + quotes, both risky

No quotes, no spaces around =. python-dotenv strips quotes if present, but unquoted is the universal convention.

BUG

BUG
HuggingFacePipeline local (TinyLlama) — "is that correct way in 2026?"

Four issues in one snippet:

1temparature → typo for temperature
2max_new_token → should be max_new_tokens (plural)
3ChatHuggingFace(llm='llm') → passed the string "llm" instead of the variable llm
4Missing torch — local pipelines run inference on your own machine, need a real ML backend installed
from langchain_huggingface import ChatHuggingFace, HuggingFacePipeline

llm = HuggingFacePipeline.from_model_id(
    model_id='TinyLlama/TinyLlama-1.1B-Chat-v1.0',
    task='text-generation',
    pipeline_kwargs=dict(
        temperature=0.5,
        max_new_tokens=100,
        do_sample=True,
    )
)

model = ChatHuggingFace(llm=llm)
result = model.invoke('What is the capital of Bangladesh?')
print(result.content)

Key distinction: HuggingFaceEndpoint = hosted API call. HuggingFacePipeline.from_model_id = downloads real weights, runs locally on CPU/GPU — the full API-vs-local trade-off from Topic 1, hands-on.

BUGTwo separate mistakes stacked: (1) os.environ['HF_HOME'] set after the import — some libs read cache paths at import time. (2) The D: drive doesn't exist on this machine.

03 Embeddings — Vectors, Similarity & a Real Mini-Project

Turning text into vectors, comparing OpenAI vs local Hugging Face embeddings, and building a working document-search project by hand.

CODE
OpenAIEmbeddings with dimensions=32 — 2026 standard?

Model choice was correct — text-embedding-3-large is still OpenAI's current premium embedding model in 2026, no deprecation. Syntax was correct too.

from langchain_openai import OpenAIEmbeddings

embedding = OpenAIEmbeddings(model='text-embedding-3-large', dimensions=32)
result = embedding.embed_query('Dhaka is the most crowded city in Bangladesh')
NOTEDefault is 3072 dims. dimensions=32 is a ~96x compression — far more aggressive than typical (256–1024 is the real-world sweet spot). Fine for experimenting, not for production retrieval quality.
BUG
embed_documents() — output looked wrong / sentences ran together.
BUG 1Missing commas between list items → Python auto-concatenated all three sentences into one merged string.
BUG 2Called embed_documents() with a hardcoded string instead of the actual documents list variable — this method needs a list, not a single string.
documents = [
    'Dhaka is the Capital of Bangladesh',
    'Sylhet is one of the most beautiful city in Bangladesh',
    'This is a beautiful Place to visit'
]

result = embedding.embed_documents(documents)   # pass the list itself

embed_query()single stringthe user's incoming search query

BUG
Import "sklearn.matrics.pairise" could not be resolved
TYPOmatrics → metrics, and pairise → pairwise
from sklearn.metrics.pairwise import cosine_similarity
PROJECT
Mini project: given 5 documents, find which one answers a user's question.

Rated 8.5/10 as a beginner project — correct algorithm end-to-end, and the code already anticipated the vector-DB problem before being told about it.

'''
Steps:
    1. Generate embedded vectors for all 5 documents.
    2. Generate embedded vector for the user's question.
    3. Compare using cosine similarity.
    4. Highest score = best matching document.
'''

from langchain_openai import OpenAIEmbeddings
from sklearn.metrics.pairwise import cosine_similarity

embedding = OpenAIEmbeddings(model='text-embedding-3-large', dimensions=300)

documents = [ "...5 cricketer bios..." ]
query = 'tell me about ms dhoni'

doc_embeddings = embedding.embed_documents(documents)
query_embedding = embedding.embed_query(query)

# cosine_similarity() needs 2D input — wrap the single query vector in [ ]
scores = cosine_similarity([query_embedding], doc_embeddings)[0]

index, score = sorted(list(enumerate(scores)), key=lambda x: x[1])[-1]
print(documents[index], score)
RESULTCorrectly matched "tell me about ms dhoni" → Dhoni's bio. Local MiniLM version scored 0.77 similarity on the same query — same correct answer, lower confidence than the OpenAI version, exactly the API-vs-local quality gap in numbers.

Own note kept from the original: re-embedding all documents on every run is costly since nothing is cached — the next real step is a vector database, so documents get embedded once and stored.
